## 1. 根因判断：产品没有反馈回路

盘点中确认的结构性问题——**这不是灵感枯竭，是信息缺失**：

- onboarding 第 5 页的「反馈问题 / 功能建议 / 留言」三个 chip 是纯 `<span>`，**没有 link 也没有 handler**（`src/components/onboarding/Onboarding.tsx:140-162`）。产品**没有任何反馈入口**。
- 没有任何埋点：不知道 307 份队伍样本哪些被导入过，不知道四个工具谁在被用。
- 没有账号（这是有意设计，不改），因此也没有用户触点。

**结论**：任何功能上线后都无法判断其价值。在补上某种反馈通道之前，路线规划只能靠推理，不能靠证据。此项未排期，但应在决定下一个大功能前先想清楚。

## 2. 方案评审结论

五个提议，owner 已逐条表态。**下面的判断理由是 owner 的原始意见，实施时不要按自己的推理覆盖它。**

### ✅ A. 赛季排名变动（Season Delta）— 完全同意

排名列表每行加一个相对上赛季的变动 chip：`↑12` / `NEW` / `↓8`。

- **判断**：完全同意，无附加条件。
- **为什么值得做**：排名变动是 meta 类产品参与感最强的元素，`NEW` 徽章天然制造回访；实现成本极低（Worker 一个 KV 写入 + 前端按 `pokemonId` join）。
- **边界说明**：本方案**不是趋势库**——只保留一份前序赛季快照、只做单次 diff，属于有边界的例外。
- **时限**：见 §3 的 P0。

### ✅ B. URL 队伍分享 — 支持

`luxraykit.com/#t=<紧凑编码>` → 打开即预览 6 只完整配置 → 一键导入本地。

- **判断**：支持，无附加条件。
- **为什么值得做**：目前整个 app **没有任何 URL 状态**（无路由 / 无 query / 无 hash），分享配置只能靠导出 JSON 或游戏内队伍码。而 Champions 的 SP 配置**至今没有任何交换格式**——做了就是事实标准。
- **契合度**：零后端、零账号、首次加载后离线可用，与「本地保存 · 无账号依赖」的定位一致。
- **注意**：这**不是**图片分享。README 曾宣传的「队伍分享图生成」代码中不存在且上一轮已砍，本次已从 README 移除。

### ⚠️ C. 对位速查（环境数据自动补全对手配置）— 支持，但需先做设计

从队伍成员出发选一个环境威胁，自动以统计上最可能的配置填充对手，给出双向伤害区间与速度先后。

- **判断**：支持。但**这个 feature 必须放在很显眼的入口**（owner 个人看法），因此**要先讨论 UI / UX / 产品逻辑**，不能直接进实现。
- **依赖**：对手配置的「最可能构筑」来自方案 E，E 未决则 C 只能退化为手填。
- **硬边界**（`docs/product/PRODUCT_SCOPE_AND_TOOL_BOUNDARIES.md`）：只能给**单次交换的伤害区间 + 速度先后**，**不得**做回合推进、换人、命中判定、特性触发链。措辞上避免「N 回合确杀」这类暗示回合推进的表达。

### ⏸ D. 先手率（对环境的速度胜率）— 支持，但优先级调后

把速度线从静态档位表变成「你的实速对环境前 N 的先手概率」，随 SP 投入实时变化。

- **判断**：支持，**但优先级往后放**。
- **理由**（owner）：**速度线功能本身就要做减法，当前 UX 不满意、太重了。**「拉 SP 实时调轴」我们自己觉得很 cool，**实则不算好的 UX**。
- **因此前置任务是**：速度线 UX 做减法（见 §3 的 P3）。在没想清楚减法方向之前加先手率，只会让这个页面更重。

### 🔬 E. 构筑聚类（从赛事队伍聚出配置原型）— 认同思路，但先调研

把当前的边际分布（道具 % / 招式 % / 性格 % 各自独立）换成真实配置的联合分布。

- **判断**：**思路认同，但当前不做**，先调研。
- **质疑一 · 样本量**（owner）：当前真实队伍样本量太小。
- **质疑二 · 信度与新鲜度**（owner）：除数据源问题外，还有**宝可梦对战环境本身在不断变化**的特点——聚类结论很难保持新鲜度，除非持续注入 fresh data，而**我们明显拿不到**。
- **关键线索**（owner）：**PokeDB 其实已经有这个 meta 了，只是我们没跟。要留意。**
- **因此下一步不是实现，而是调研**：见 §3 的 P4。如果 PokeDB 已提供，正确做法是接入而非自建聚类。

### ~~P1 — 方案 A 赛季排名变动~~ ✅ 已落地（2026-08-05）

实现与原计划有一处**有意的偏离**：没有新建 `environment:previous-season` KV key，而是把前序名次表放进 `environment:latest` 内部的 `previousSeason` 字段。理由是 `/api/environment/latest` 目前把 KV 里的文本**原样**返回（不反序列化再序列化 437KB），独立 key 会逼它多一次读 + 拼装；放进快照还顺带让离线客户端从已缓存的那份里直接拿到 delta。

- **共享逻辑** `src/lib/seasonRankDelta.ts`：类型 + `isImmediatePredecessor` / `selectSeasonRanks` / `resolveSeasonRankDelta` / `describeSeasonRankDelta`，Worker 与前端同源。
- **Worker** `resolvePreviousSeasonRanks`：三级取值（带过 → 就地压缩旧快照 → 从 PokeDB 现抓 `?season=n-1`），失败不阻断发布。细节见开发指南 §6.3。第三级是上面那条「PokeDB 保留历史」结论的直接产物，也是「即使这次没赶在换季前部署也能补回来」的保证。
- **前端**：`EnvironmentState.previousSeason` + 榜单行 chip（↑n / ↓n / NEW / `—`），首页 Top5 与完整榜单都有；数据口径页多一条「变动」说明。
- **三条硬约束**（已写进开发指南 §5.3，勿绕过）：只对比紧邻上一赛季；无前序快照则完全不渲染 chip；chip 表达的是**名次**变化而非使用率变化。
- 测试：`seasonRankDelta.test.ts`（13）、Worker 换季与回补 6 例、`environment.test.ts` 的跨赛季守卫、`EnvironmentPage.test.tsx` 的渲染与「无数据不渲染」两例。

**尚未验证的部分**：线上真实换季行为要等 PokeDB 放出 M-5（预计 2026-08-05 15:30 UTC 前后的每日发布窗口）。合并后可用 `/api/environment/status` 的 `previousSeasonLabel` 确认。

**已知覆盖缺口**：chip 没有视觉基线——视觉用例只 route 静态快照，而 `previousSeason` 只有 Worker 会写。补这层要先决定视觉用例怎么表示 Worker 来源的数据，属独立设计题，已记进 `docs/qa/MOBILE_VISUAL_REGRESSION.md` 的缺口清单。
